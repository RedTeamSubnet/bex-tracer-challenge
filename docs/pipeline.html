Pool to Score

A challenge that turns one browser question — which extensions are installed right now? — into a number between 0 and 1. The idea first, then every mechanism behind it.

Current implementation (2026-09-26). The pool contains 89 names in 8 groups. Each score runs 6 sequential rounds with 12 enabled extensions, rotates unpacked-extension IDs per round, and evaluates one JavaScript file per group.

  • build time — once, inside docker build
  • request time — per POST /score
  • failure · open risk
Part one The idea

01The game

We publish a fixed list of 89 real Chrome extensions in 8 groups — ad blockers, developer tools, password managers, media tools, VPNs and workflow helpers. Every one is downloaded from the Chrome Web Store, but its store ID is never used at runtime.

Each round we secretly enable a random handful of them in a fresh Chrome, open an ordinary-looking web page, and run the miner's JavaScript on that page. The miner returns one true/false per extension. We compare that against what we actually enabled.

That's the whole challenge. The difficulty is that a browser extension is supposed to be invisible to the pages it runs on — so the miner has to find the traces they leave anyway.

02Where it runs

We don't run this loop ourselves. A subnet validator does, on its own schedule, against every miner competing on the challenge. Our container exposes GET /task, authenticated POST /score, and an authenticated GET /results report for the most recent run.

volumes/configs/ is currently tuned down for laptop testing: n_rounds: 5, k fixed at 5. Note that a fixed k removes a real property — with k varying, cardinality is part of what the miner has to get right; pinned, precision and recall are forced equal and false positives stop costing anything.

03What makes it hard, and where it's fragile

An extension can be detected only through something it actually does. Four classes of signal exist, and they are not equally available.

Open risk — installed is not observable

Some extensions stay idle until onboarding, account login, a toolbar action, or a visit to a specific site. If they leave no page-visible behavior on the bait page, their labels cannot be earned directly. This affects all miners equally, but lowers the measurable ceiling.

The pool intentionally remains a competitive target rather than a promise that every label is detectable. Use screen_extensions.py and visible local rounds when curating it.

Resolved shortcut — static resource tables

Store IDs and resource paths may be public, but they do not identify the unpacked extension: each round's secret staging path produces a fresh Chrome ID.

Miners therefore need behavioral detection instead of one shared chrome-extension:// lookup table.

Part two The mechanism

04Two lifetimes of one YAML file

extensions.yml

extensions.yml is read twice, by two programs that never run at the same time and share nothing but a directory on disk. At build time fetch_extensions.py uses id, sha256 and version to fetch and verify real signed extensions. At request time _pool.py reads each entry's name, group, and store ID.

05Verifying CRX identity, rotating runtime IDs

scripts/fetch_extensions.py — build time only

Store .crx manifests carry no key field. The script verifies that a CRX signing key derives the pinned store ID, then deliberately leaves the key out of the unpacked manifest. Chrome therefore derives the runtime ID from the per-round staging path.

The extension still loads and works, but lives at a fresh chrome-extension://<hash-of-secret-path>/ each round. A static probe against the store ID fails by design, forcing behavioral detection.

06One round, start to finish

api/endpoints/challenge/_browser.py · service.py

The miner's files are served, not injected. Before the rounds start, service.py stages all eight <group>.js files under templates/static/detections/. The bait page loads them with ordinary <script src> tags. Stubs are restored afterwards so miner code never outlives the run that sent it.

07Scoring

api/endpoints/challenge/_payload_manager.py

Known property

max(0.0, mcc) clamps per round, before averaging. Negative correlation folds up to zero, so a zero-information guesser scores about 0.08 — and because that is bias rather than variance, averaging more rounds does not remove it. Clamping the run mean instead would let negative rounds cancel positive ones and drive a guesser to 0.

08When something breaks

Miner-caused failures score 0.0 and stay in the denominator. Infrastructure failures are excluded because a dead browser is not evidence about the miner. If too many browsers fail, the request fails instead of returning a thin average. 

BrowserError       all miner groups failed, timed out, or returned junk
                   -> round scores 0.0, run continues

BrowserInfraError  Chrome would not start, an id did not load, tab crashed
                   -> excluded; if more than 20% of rounds fail
                      this way, /score RAISES instead of returning a number

RuntimeError       pool missing, k >= pool size
                   -> 500 before any round runs
Why the infra split matters

Returning 0.31 because our browsers died looks exactly like a weak miner and would be recorded as their score. Failing the request instead makes it unmistakably our problem. One scoring run at a time is enforced by a non-blocking lock — a second concurrent call gets 429 rather than thrashing the box and corrupting every round's timing.

The invariant everything protects

rec.enabled exists only in Python memory. It is never written into the bait page, exposed as a global, passed as a query parameter, or included in the report — which publishes n_enabled, never enabled names or ids. The miner's only route to it is observing what the extensions actually do.
