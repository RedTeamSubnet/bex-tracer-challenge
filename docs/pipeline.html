Pool to Score

A challenge that turns one browser question — which extensions are installed right now? — into a number between 0 and 1. The idea first, then every mechanism behind it.

Out of date (describes the 2026-09-01 design). The diagrams below show a 27-extension pool, a single solution.js, detection by extension id and 20 rounds. All of that has changed: rounds now run sequentially, the pool is 45 extensions in 6 groups and published by name, ids rotate every round, a submission is one file per group, and the container has no internet. The flow itself is still accurate. For current facts see docs/README.md.

Part one The idea

01The game

We publish a fixed list of 27 real Chrome extensions — ad blockers, password managers, translators, shopping helpers. Every one is downloaded from the actual Web Store and loaded under its real store ID.

Each round we secretly enable a random handful of them in a fresh Chrome, open an ordinary-looking web page, and run the miner's JavaScript on that page. The miner returns one true/false per extension. We compare that against what we actually enabled.

That's the whole challenge. The difficulty is that a browser extension is supposed to be invisible to the pages it runs on — so the miner has to find the traces they leave anyway.

02Where it runs

We don't run this loop ourselves. A subnet validator does, on its own schedule, against every miner competing on the challenge. Our container answers two HTTP endpoints and nothing else.

volumes/configs/ is currently tuned down for laptop testing: n_rounds: 5, k fixed at 5. Note that a fixed k removes a real property — with k varying, cardinality is part of what the miner has to get right; pinned, precision and recall are forced equal and false positives stop costing anything.

03What makes it hard, and where it's fragile

An extension can be detected only through something it actually does. Four classes of signal exist, and they are not equally available.

SignalHow it worksReach
web-accessible
resources		 Fetch chrome-extension://<id>/some/file.css. Resolves if installed, rejects if not. Deterministic. 17 / 27
page footprint Injected stylesheets, rewritten colours, stamped attributes, shadow roots. 1 confirmed
request blocking Blockers kill tracker requests before the network. Which hosts die is a fingerprint. 3 of 4 blockers
gesture-triggered Password managers inject only after a real click and keystroke on the field they watch. 5 candidates
Open risk 1 — installed is not running

A chrome-extension:// fetch succeeds because the extension is installed. It succeeds just as well when the extension's logic never executes. So 17 of 27 labels are answerable with the extension completely idle.

At least two are idle by construction: Ghostery ships all 33 of its blocking rulesets with enabled=False until a human completes onboarding, and Bitwarden has no page footprint without an unlocked vault. An extension that never acts is a label no miner can earn.

Open risk 2 — everyone writes the same file

The pool is fixed, so the web-accessible-resource paths are fixed too. There is one sensible way to write that lookup table, and every competent miner writes it.

The validator similarity-checks submissions against each other and zeroes anything above the threshold. Two honest miners doing the correct thing independently produce near-identical files and both score nothing. Rotating the pool, or removing the shortcut entirely, is what fixes this.

Part two The mechanism

04Two lifetimes of one YAML file

extensions.yml

extensions.yml is read twice, by two programs that never run at the same time and share nothing but a directory on disk. At build time fetch_extensions.py uses id, sha256 and version to fetch and verify real signed extensions. At request time _pool.py reads only the id.

05Loading extensions under their real IDs

scripts/fetch_extensions.py — build time only

Store .crx manifests carry no key field — the Web Store rejects uploads that have one, and Chrome injects it at install time. Loading unpacked skips that step, and without it Chrome derives the extension ID from the directory path.

The extension still loads. It still works. It just lives at chrome-extension://<hash-of-a-path>/ — so every probe against the real store ID fails, all published prior art is useless, and the challenge is quietly unsolvable. Recovering that key is most of what this script does.

06One round, start to finish

api/endpoints/challenge/_browser.py · service.py

The miner's file is served, not injected. Before the rounds start, service.py writes it to templates/static/detections/solution.js, which the bait page loads with its own <script src> — the same model ab_sniffer and ada_detection use. The stub is restored afterwards so a miner's code never outlives the run that sent it.

That comma-separated path list is how extensions get enabled — a Chrome command-line flag, not a Selenium API. Never options.add_extension() (a different code path, with different ID derivation) and never a BiDi install.

07Scoring

api/endpoints/challenge/_payload_manager.py

Known property

max(0.0, mcc) clamps per round, before averaging. Negative correlation folds up to zero, so a zero-information guesser scores about 0.08 — and because that is bias rather than variance, averaging more rounds does not remove it. Clamping the run mean instead would let negative rounds cancel positive ones and drive a guesser to 0.

08When something breaks

A failed round scores 0.0 and stays in the denominator, so browser flakiness is indistinguishable from a bad miner — except that one is our fault. The code separates them. 

BrowserError       the miner's script threw, timed out, or returned junk
                   -> round scores 0.0, run continues

BrowserInfraError  Chrome would not start, an id did not load, tab crashed
                   -> counted separately; if more than 20% of rounds fail
                      this way, /score RAISES instead of returning a number

RuntimeError       pool missing, k_max > pool size
                   -> 500 before any round runs
Why the infra split matters

Returning 0.31 because our browsers died looks exactly like a weak miner and would be recorded as their score. Failing the request instead makes it unmistakably our problem. One scoring run at a time is enforced by a non-blocking lock — a second concurrent call gets 429 rather than thrashing the box and corrupting every round's timing.

The invariant everything protects

rec.enabled exists only in Python memory. It is never written into the bait page, exposed as a global, passed as a query parameter, or included in the report — which publishes n_enabled, never the ids. The miner's only route to it is observing what the extensions actually do.
